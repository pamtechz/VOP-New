# VOP curriculum authoring — review proposal

Status: **draft for product approval.** This is not a migration or an instruction to publish the prototype to production. The existing Firestore lessons and classic authoring path must stay intact until explicitly approved.

## 1. Product model

| Entity | Meaning | Learner-facing representation | Authoring permissions |
| --- | --- | --- | --- |
| Program / Course | An organizational or platform-wide learning offering (e.g. a Bible school course, Master Guide training) | Course catalogue tile and course home | Super Admin globally; authorized org/hierarchy creators only within owned scopes |
| Guide / Module | A curriculum unit assigned to a program | Ordered guide/module card | Its owning author/admin, with platform stewardship respected |
| Lesson | Unit for enrollment, completion, progress and quizzes | A lesson when the program is in **lesson navigation** mode; a grouping label otherwise | Scoped curriculum editor |
| Chapter | Editorial grouping within a lesson | Collapsible table of contents | Scoped curriculum editor |
| Section / Page | One complete learner study page | A numbered, individually navigable page | Scoped curriculum editor |
| Plate block | Paragraph, heading, list, quote, image or other approved content in a section | Rendered inside the selected page | Scoped curriculum editor |
| Assessment | A private-bank quiz anchored to guide, lesson, chapter, section or stable block ID | Assessment action at the relevant scope | Quiz-authoring permission; keys never embedded in public pages |

**Important:** Even when a program chooses section-first navigation, the Lesson remains a real backend entity. Hiding that layer must not change progress, quiz association, certificates, enrollment, or audit history.

## 2. Example navigation

Program: Voice of Prophecy → Guides/Modules: Bible Study I, Bible Study II → Lesson: The Sabbath → Chapter: The Biblical Sabbath → Section 1: Creation → Paragraphs, illustrations, Scripture references → Section 2: Rest → Paragraphs, quiz → Chapter/Guide examination.

- **Lesson navigation:** Program → Guide → Lesson → Chapter → Section/page.
- **Section navigation:** Program → Guide → grouped section/page cards, with the owning lesson and chapter shown as breadcrumbs. Clicking a card opens the underlying lesson at that exact page index.
- Both modes use one canonical content tree and identical completion rules. The program owns the navigation preference; a guide can retain its legacy setting as a migration fallback.
- A section is a deliberate author-created learner page, not an arbitrary fixed character count or every paragraph. Authors work in one continuous Plate document per chapter. “Start section” inserts an editor-only boundary immediately before the selected paragraph/heading; that paragraph remains a normal content block with its existing block ID. On save, boundaries are projected back to canonical section records and are never stored as learner content.

## 3. Target data relationships

First-class tenant-aware `programs/{programId}` records in this prototype:
```ts
{
  id, title, description, coverImageUrl, guideIds: string[],
  ownerUid, ownerOrganizationId, ownerTenantId, organizationId,
  scope: 'platform' | 'organization',
  sharingScope: 'private' | 'organization' | 'shared',
  entryMode: 'lessons' | 'sections',
  published, archived, createdAt, updatedAt
}
```
Hierarchy administrators can create programs for authorized descendant organizations; hierarchy-wide records are **not yet enabled**. This avoids silently broadening access to private descendant guides.

The current prototype stores ordered `guideIds` on the program itself, allowing safe reuse of the same canonical guide in more than one program. **Do not change guide IDs**. A future indexed reverse lookup can be added without duplicating lesson documents. Existing `guides/{guideId}/lessons/{lessonId}` remains authoritative. Its chapter/section hierarchy gains a validated `section.document` Plate JSON value. Existing `pages`, `contentPages`, and flattened `blocks` remain compatibility projections generated by the server, not separate authoring sources.

Keep **Learning Paths** separate: a pathway can arrange multiple programs or guides; it is not automatically the same object as a course.

## 4. Intended editor UX

1. Courses catalogue: search/filter by scope, publication, type and language. Creating a program specifies ownership, navigation mode and visibility. Users see only resources authorized for them.
2. Open program: reorder/assign guides or modules and manage final examinations. Show draft, published, empty and loading states.
3. Open guide: create/reorder lessons, or manage them as the internal container when the program is section-first.
4. Open lesson: compact header + Chapter selector + a small learner-page outline + one continuous Plate paper-style canvas for the selected chapter. There are no separate section editors and no manual block-form stack. Authors write naturally, then put the cursor in the paragraph/heading that should begin a new learner page and choose **Start section**. The outline provides page naming, ordering, duplication, chapter moves and section quiz access without fragmenting the writing canvas.
5. Plate toolbar: undo/redo, paragraph/headings, strong/emphasis/underline/strikethrough/inline-code, lists, quotations, safe HTTPS images/links, approved audio/video resolved through the existing `/api/media` allowlist, **Start section**, and context actions for section/block quiz anchors. Further items such as tables, galleries, interactive forms, AI writing and collaborative comments are **not** part of the reviewed core unless separately implemented and tested.
6. Save draft/preview/publish are explicit. Invalid editor state cannot be silently discarded or published. Preview uses exactly the validated learner renderer and actual section-page order.

## 5. Security, stewardship and lifecycle

- Program creation/edit/publish must be checked by the server and Firestore rules against platform/organization/hierarchy scope. Super Admin works platform-wide without mandatory org selection.
- An organization cannot reparent someone else's guide or claim another organization's private language or program. Shared/adopted content remains under platform stewardship.
- Quiz questions/keys stay in the private Quiz Library; publication exposes only approved prompts and references.
- Validate Plate JSON server-side using allowlisted nodes and safe public HTTPS URLs. Never render stored raw HTML or execute arbitrary embeds. Reject unsupported nodes rather than silently drop substantive content.
- Drafts and published revisions should be separate immutable snapshots when rollout is approved. Stable section/block IDs preserve bookmarks, resume positions and quiz anchors during non-destructive edits. A delete/move checks dependencies before changing references.
- Legacy readers and lessons remain functional; migration is per lesson, explicit, reversible until the first published Plate revision. Include backup, diff/preview and rollback paths.
- Firestore is authoritative. Device storage is an offline cache only; tenant-scoped reads and writes must be enforced even when data is stale.

### Existing privacy gap to address before rollout

The draft now writes instructor notes atomically to `guides/{guideId}/lessons/{lessonId}/private/instructorNotes`, removes the public `teacherNotes` field, and reads notes through the permission-checked admin API. Firestore rules deny clients, including direct Super Admin clients, access to the private subcollection. Historical lessons **remain exposed until explicitly migrated**. The repository includes a dry-run-first, conflict-aware tool at `scripts/migrate-lesson-instructor-notes.mjs`; running it against production requires a separate approved, backed-up operation and explicit project confirmation. This is an existing data-design issue, not a feature of Plate.

## 6. What the current PR demonstrates

**Implemented in the draft:** A React/Vite Plate editing surface used as the sole structured-lesson editor, compact sticky toolbar, one continuous chapter document with editor-only section/page boundaries, stable block IDs when paragraphs become section starts, compact learner-page outline, approved media insertion, safe JSON-to-reader rendering, rich formatting, draft save through the existing lesson API, guarded transfers, first-class Course/Program CRUD, tenant-constrained ordered guide assignments, course-first learner catalogue, direct section-first admin/learner navigation, API-only program writes and rules tests, and segregated instructor notes for new/edited lessons.

**Still requiring product approval and controlled follow-up:** Historical note migration, published immutable revision history and rollback, guide-to-program navigation from every older entry point, accessibility review, program-wide hierarchy scope if desired, and verified real-device authenticated editor interactions. The old guide-level navigation preference remains a fallback for legacy guides that are not opened through a program.

Do not merge this PR or deploy it merely because CI passes. Approval should cover the canonical entity hierarchy, the program navigation mode, the continuous-authoring section-boundary behavior, the direct section-first learner navigation, and the staged migration boundaries.
